How baitbook is put together

A guide to the Angler (the engine on the PC) and the two apps that talk to it, from the whole system down to a single prompt turn. Every box names the file or function it stands for, so you can jump from a diagram straight into the code.

server.py, __main__.py: the API engine.py llm.py, prompts.py imagegen.py, ComfyUI db.py, media.py, data/ config.py, baitbook.toml web/app/, pcapp/ web/device/ web/shared/ pairing, tokens outside the repository a state

1. The big picture

baitbook is a social feed with no humans in it. Every "user" is a resident the owner creates from 5 images, and every post after those 5 is an image-to-image edit of an older image. The owner bites or throws back each post, and those votes steer what gets made next. There are three programs:

  • The Angler (angler/, Python): the engine and the only server. One process runs the HTTP API, serves both apps' files, and owns the language model in-process through llama-cpp-python. It drives the image model through a ComfyUI server that it starts and stops itself: baitbook's own (baitbook comfyui, section 11) or one the user already has. baitbook angler runs it in a console; the PC app starts it in the background.
  • The PC app (web/app/, opened in a native window by pcapp/, which the baitbook command runs): the owner's console and an online feed. It talks to the Angler directly; votes land the moment they are cast.
  • The phone app (web/device/): an installable web app that keeps its posts, images and votes in IndexedDB. It works with no network and docks with the Angler to send votes home and fetch the last 7 nights.
  • Not in the repository: the model files (Gemma 4 31B and its mmproj; klein 4B's files in ComfyUI's model folders; baitbook models downloads them), the ComfyUI install and its Python environment (baitbook comfyui puts one in the home folder), and the home folder, which holds baitbook.toml and data/, and comfyui/ and models/ once those two commands have run (section 14). baitbook.toml points at the models and ComfyUI.

2. Inside the Angler

The Angler is one Python process with one composition point: FastAPI's startup hook in server.py loads the config, opens the database and builds the one Engine. Its shutdown hook stops a ComfyUI the Angler started. Everything that touches a model goes through the engine; everything that crosses the network goes through server.py. The modules are layers with a direction: the server calls the engine, the engine calls the model wrappers and the store, and nothing below the engine knows there is a web server at all.

One rule explains most of the structure: there is one GPU, and only one job may use it at a time. Every piece of work that touches a model (a vision read, a night shift) is a job on the engine's one queue, run by its one worker thread. The HTTP handlers never call a model: they queue a job, and the apps poll /api/status to watch it (section 5). Inside a night shift the same rule goes one level further: the language model and the image model run in series, never together (section 12).

4. Boot

There are two ways in, both through the baitbook command (baitbook/cli.py). baitbook (or baitbook app, or baitbook-app, which the app icons open with no console) runs pcapp, which opens the PC app on an Angler and starts one in the background if nothing answers. baitbook angler runs the Angler alone, in a console. python -m angler and python -m baitbook still work. Either way the Angler process is the same, and nothing loads a model at boot: the language model loads when a job needs it, and ComfyUI starts when a night shift reaches its image phase. The other subcommands, stop, status, phone, setup, comfyui, models and shortcut, start no Angler. baitbook comfyui won't even run while one answers, since the ComfyUI it repairs may be in use.

  • Config is read twice on purpose. __main__ needs [server] before the app exists; _start() loads it again inside the server process. After that every module asks config.section() each time, so an edit from the PC app takes effect on the next job without a restart (section 14).
  • The pairing code is per process. pair_code() draws six random digits the first time it is asked (by __main__, which logs it), and the PC app shows it in Settings. A restart, or 5 wrong tries, makes a new one; tokens already handed out stay valid (section 16).
  • No teardown of jobs, but a recovery. The worker and scheduler are daemon threads, so stopping the Angler stops them mid-job; finished posts are kept. Jobs live only in memory, so at the next start Engine._recover() marks any shift still at running as interrupted, and queues the vision read again for any resident still at reading.
  • Stopping it. baitbook stop calls POST /api/shutdown on the Angler on this machine, then waits up to 30 s for it to stop answering. Only this machine may call that route (is_local()), so a PC app paired as the owner gets a 403. The route answers first, then sets should_exit on each uvicorn server through app.state.stop, which main() set. Uvicorn then runs the shutdown hook, server._stop(), which stops a ComfyUI the Angler started (stop_started_comfy()), so it doesn't sit on the GPU. While a job runs, baitbook stop refuses without --force; a shift cut off that way is marked interrupted at the next start. Ctrl+C stops a baitbook angler running in a console.
  • One Angler per data folder. Before anything opens the database, main() takes an OS lock on data/angler.lock (msvcrt.locking on Windows, flock elsewhere). It is held until the process ends, however it ends. A second Angler on the same data, on any port, logs "Another Angler is already running on …; this one exits without touching it" and exits with status 1. Without the lock, its _recover() would mark the running Angler's shift interrupted before its bind failed. Once its ports are bound, the Angler notes its loopback port in data/angler.port and removes the note when it stops. baitbook status, stop and the PC app look there (config.angler_port()), so they find one started with --port; a note is only believed while the lock is held, so one left by a killed Angler is ignored. data_in_use() asks without keeping it: it takes the lock and unlocks at once (on Windows explicitly, since a close lets go of a lock only eventually).
  • Bind first, then start. Uvicorn runs the app's startup before it binds, so main() binds the socket(s) itself and hands them to uvicorn.Server.run(sockets=…). A port that is taken is a clear error ("Can't listen on …") and an exit, before the engine exists.
  • With HTTPS on, there are two listeners. [server] ssl_certfile makes the main port HTTPS. A second uvicorn.Server serves the same app over plain HTTP on 127.0.0.1:[server] local_port (8788). It runs in a thread with lifespan off, so the startup runs once, and it answers only once the main server has started. pcapp opens that listener, so no certificate has to name 127.0.0.1 (section 17).

5. One worker, one GPU job

Engine (angler/engine.py) owns everything that touches a model. Work arrives through submit(kind, **args), waits on one queue.Queue, and is run by one thread, angler-worker, one job at a time. The worker publishes what it is doing into a status dict, and the apps read a copy of it from GET /api/status. Nothing waits on a job: the HTTP handler that queued it has already answered.

stateMeaning
idleNothing running. next_run says when the schedule fires, or null when it is off.
startingThe worker has taken a job (job says which) and it hasn't set its first phase yet.
readingA vision read; resident names who, items has one entry per seed image plus one for the mood tags.
writingA night shift, phase 1: the language model is writing prompts and captions.
editingA night shift, phase 2: the image model is editing.
errorThe last job raised. error holds the message, every item it had not finished says stopped, the journal has an error event, and the next job clears it.

6. A resident is born

A resident starts as a name, a handle, a bio and 5 images. create_resident in server.py stores the images first (a file that isn't an image is a 400, and the ones already stored are deleted, so nothing is left and the upload can be tried again), then records the resident with status = 'reading' and the images as its seed posts (kind = 'seed', night 0) in one transaction, and queues a read job. The read is Engine._read: one conversation with the language model, with two jobs. It writes a base prompt for each seed image, then 3 to 5 mood tags for all of them together. The same job runs again from the resident's card: "Read again" after a read failed, or "re-read" to rewrite the base prompts (POST /api/residents/{id}/read).

  • Temperature 0.4. [text] read_temperature: the read is description, not invention. A prompt may run to 320 tokens; the tags to 60.
  • Each prompt must stand alone. The model sees the earlier images, so both read_system and every read_ask tell it never to write "same as before". A base prompt is later edited on its own, with no other image in sight.
  • Watermarks and dates are left out. Images saved from the web carry @handles, signatures and dates. Copied into a base prompt, they would be copied into every edit after it. read_system asks for the picture as if they were not there, and each read_ask repeats it. Text that belongs to the picture, like a sign in the scene, stays.
  • A read that fails leaves the resident failed. _read sets the status before the error reaches the worker. Night shifts skip the resident until a read finishes, and the card offers "Read again". A read cut off by a restart is queued again by _recover().
  • The tags are tidied. parse_tags splits on commas and newlines, lowercases, strips stray punctuation and quotes, drops duplicates and keeps 5. If nothing usable comes back, the resident gets ["quiet"]. The owner can rewrite them on the resident's card (PATCH /api/residents/{id}).
  • It is slow by design, and a little slower than it needs to be. About three minutes for 5 images. The multimodal chat handler re-encodes every image already in the conversation on each turn, so turn 5 encodes five images. That is fine for something done once per resident; a projector cache would remove it.

7. A night shift, end to end

A night shift is Engine._shift(trigger). It makes [shift] posts_per_resident new posts for every resident whose read has finished, and every one of them is an image-to-image edit of an older image. It runs in two phases, in series. First the language model writes every prompt and caption for the night and unloads. Then the image model renders every edit. The two never hold the GPU together (section 12).

  • Who takes part. Residents with status = 'ready' and at least one source. A resident whose read is still running, or who has no usable source, is skipped for the night.
  • Picks differ when they can. Sources are drawn with rng.sample, so a night edits different images. Only a resident with fewer sources than posts_per_resident gets an image edited twice, and then the "never repeat a prompt" rule and different directions keep the two edits apart.
  • Each edit is told what to change. write_edit gives every edit its own directions (the place, the moment, the camera…), and sends a prompt back once if it comes back too close to what exists (section 9).
  • A shift that raises is marked failed, with the message in the row's error and the posts it made so far counted. The worker writes the journal and the status.
  • Captions. Up to 48 tokens, the first line only, at most 140 characters, lowercased.
  • A fresh seed per edit. rng.randrange(1, 2**31), stored on the post.
  • Tags. Each new post gets the resident's first four mood tags, through slug().

What the apps see

While a shift runs, status.items has one entry per pick: the resident, the source's id and image, the turn number, what the edit was asked to change (change, shown on the row) and how close its prompt stayed (similarity), and a stage that moves forward as the shift does. The Night shift view in the PC app draws each item as a row: the source image fades until its edit lands on top of it.

8. Sources, examples, chains

Two things decide what a night shift makes: which old image each post edits, and what the language model is shown about the owner's taste. The first is Engine._sources, the second Engine.context. Both read only the database; votes count the moment they reach the Angler, from the PC app directly or from a phone when it docks.

The Memory view shows this exactly. GET /api/residents/{id}/memory calls the same context() with a fresh random draw and returns the full system prompt plus which bites and throw-backs were sampled; "Re-roll the sample" simply asks again. Nothing is saved, so the next night shift draws its own sample.

Bites, throw-backs and snags

The owner has three verdicts for an edit, and they teach the Angler different things:

VerdictMeansAs a sourceAs an exampleIn the feeds
bite (vote = 1)more like thisyesgood, up to [shift] good_examples (5)stays
throw back (vote = −1)not this ideanever again: its line of edits stopsbad, up to [shift] bad_examples (3)leaves the phone at the next dock
snag (snagged_at set)a broken render: wrong anatomy, garbled detailneverneverleaves both at once; the image files go at the next night shift
  • Why more good examples than bad. A bad example is a whole prompt that the model must read, then guess what was wrong with it. This model also copies wording readily, so a full bad prompt in its context can leak into a new one. And a throw-back already has a stronger effect without any examples: its image is never edited again, so that branch dies. So the defaults are 5 and 3. With bad_examples = 0, shift_system(…, with_bad=False) leaves out the bad-examples section and its rule entirely, rather than showing an empty heading.
  • Why a snag is not a throw-back. Before snags, a render that came out broken could only be thrown back. That taught the model "the viewer dislikes this idea" when the failure was the image model's. Worse, an unvoted broken post is a source the next night, and since an edit is made from its source image, the breakage would carry into the next post. A snag takes the post out of everything without teaching anything.
  • The snag rate measures the image model. The bite rate is about taste; the snag rate is how often renders come out broken: snags ÷ every edit made. Snags count even after their images are cleared, since the row stays (db.count_snags). The PC app shows it overall (the Feed's side card), per resident (their card) and per night (History: db.shifts() adds n_snags). Per night is where it helps: after changing steps, size, the variation or the image model, the next nights show whether renders break more or less.
  • A snag can be undone until the next night shift. Snagging only sets snagged_at: the PC app's toast and the Ledger's "snagged" filter offer undo, and so does the phone's toast. An undo on the phone after a dock took the snag out (while that dock is still out, or if it never came back) goes home with the next dock as an unsnag; once a dock has come back, the post is off the phone and the PC app's Ledger is where to undo it. At the start of each shift, db.purge_snags() sets the snags' image to null and the engine deletes their files. The row and its prompt stay, so a chain that passes through a snag still adds up (the prompt panel shows it as a dashed "snag" link), and the prompts of broken renders stay on record.

9. The prompts

Every word the language model sees is in angler/prompts.py. There are two conversations, and the image model's prompt primer opens both. By default that is KLEIN_PRIMER, the rules for writing FLUX.2 [klein] prompts (4B or 9B): narrative prose, subject first, then setting and light, style and finish, composition and colour, about 30 to 100 words, no tag lists, no weight syntax. primer(image_cfg) reads [image] primer_file instead when it names a file, so a different image model brings its own rules.

How far an edit moves

The first build asked for an edit with "Change one or two things… Keep the rest". Gemma 4 31B took that literally. It copied the source prompt and changed a word or two, so most edits shared nearly all their wording with their source ("one hand" became "both hands", a line of text changed). One edit even changed "both hands" back to "one hand", recreating the seed's own prompt. With the source passed in as a reference, klein then made an image that was almost the same. Three things now push edits apart:

  • Directions. pick_directions draws what each edit must change, by weight, without repeats: the place (3), the moment (3), the time and weather (2), the outfit (2), the camera (2), a new detail (2), the mood (1), and the medium (1, only at wild). edit_ask lists them, and the status row shows them ("changing the place + the camera").
  • The rules. shift_system asks for a new post rather than a retouch: an obvious change, the subject and look kept, written in fresh words rather than the old sentences.
  • A check. write_edit compares the reply word by word (difflib) with the source, the base prompts and tonight's earlier prompts. Above the variation's limit, it asks once more with too_close() and keeps whichever reply is further away. The rejected try is left out of the conversation.
[shift] variationDirections per editAsked once more aboveThe extra sentence
subtle190% the same"Keep the change small but clearly visible."
bold (default)275%"Make it a clearly different picture."
wild3, the medium included60%"Be daring: it can surprise, as long as it is still recognisably theirs."

Measured during development with the same two residents, by the same word-level similarity() the check uses: the first build's two nights (12 edits) were 47 to 98% the same as their sources, 79% on average. A test run of six bold edits came out 29 to 49% (mean 37%), and none needed the second ask. The next real night shift came out 36 to 53% (mean 40%). Every edit kept the resident's subject and style.

10. The language model

LanguageModel (angler/llm.py) runs the language + vision model in-process through llama-cpp-python. The default is Google's Gemma 4 31B QAT GGUF (Q4_0, 17.7 GB, from google/gemma-4-31B-it-qat-q4_0-gguf) with its mmproj (1.2 GB), loaded with llama-cpp-python 0.3.36 in the build the installer picked for the GPU (HIP on this machine). The model is loaded only for a job and unloaded after it, so it holds no memory between jobs. Any Gemma 4 GGUF and its mmproj can stand in for the default; other model families can't, because load() always builds a Gemma4ChatHandler and n_batch is sized for Gemma 4's images.

  • llama-cpp-python is optional. It is the llm extra, built per GPU, and load() imports it only when a job needs the model. Without it everything else runs (the tests and CI never install it), and a job that needs the model fails with LLMError: "llama-cpp-python is not installed". baitbook setup checks for it and says whether it can use the GPU.
  • Images go in as data URIs. image_part(png) base64-encodes the PNG master into an image_url part; the chat handler hands it to llama.cpp's projector.
  • The handler talks too much. MTMDChatHandler prints the whole rendered prompt to stdout, so Engine._chat wraps every call in redirect_stdout. The native projector's own lines (image encode timings) still reach the console; they are harmless.
  • Why the retries. GPU memory freed by ComfyUI, or by the previous load, comes back a moment after the call that freed it returns. A load straight after a swap can fail once with ValueError; load() waits 8 s and tries again, four times in all.

11. The image model

The image model is FLUX.2 [klein] 4B by default (Apache 2.0, as safetensors; klein 9B works too, under a non-commercial licence, as safetensors or GGUF files; other image models don't, because klein_i2i.json is built from FLUX.2 nodes), and it only ever edits: every new image is made from an older one, with the source image passed in as a reference latent and the edit prompt describing the whole target image. It runs in ComfyUI, which is a separate server; ComfyClient (angler/imagegen.py) is the Angler's only contact with it.

baitbook's own ComfyUI

baitbook comfyui (baitbook/comfyui.py, also offered by baitbook setup) installs a ComfyUI just for baitbook, in comfyui/ in the home folder. Each step is skipped when it's already done (only the requirements are checked again every time), so running it again repairs or upgrades:

  • The code: a pinned release (comfyui.VERSION, 0.39.0), from its zip on GitHub (no git needed), in comfyui/ComfyUI-<version>/. No ComfyUI Manager: the Angler only uses the API.
  • Python: a 3.13 environment of its own, comfyui/.venv, made with uv (the uv package is a dependency, for machines where uv isn't on PATH).
  • PyTorch, as ComfyUI's README gives it for the GPU gpu.detect() finds (BAITBOOK_GPU or --gpu overrides it).     • AMD on Windows: AMD's ROCm 10 wheels, with only this GPU's kernels (device-gfx1100, say) when the name gives the architecture away, else device-all;

  • Where things go: models, custom nodes and outputs live in comfyui/ itself, which ComfyUI is started with as --base-directory, so a new version replaces only the code folder.
  • The config, written last, once the rest has worked: comfy_dir, comfy_python, comfy_base and comfy_url (all LOCAL_ONLY). comfy_url keeps its port if that port is free and isn't 8188; otherwise it gets the first free one from 8190 (up to 8299). A ComfyUI the user already has works too: baitbook setup asks for its folder, or comfy_dir and comfy_python can be set by hand, with comfy_base left empty. baitbook comfyui was checked by hand on the owner's machine (section 22).

Downloading the models

baitbook models (baitbook/models.py, also offered by baitbook setup after the ComfyUI step) downloads the default models from Hugging Face, about 35 GB in all. They are Apache 2.0 and need no sign-in.

  • Pinned: each file in models.DEFAULTS is fixed to a commit, with its size and sha256, so what lands is what was tested.
  • Where: Gemma's GGUF and mmproj go into models/ in the home folder. klein 4B, its text encoder and its VAE go into ComfyUI's models folder (under comfy_base, or comfy_dir), so they wait until there is a ComfyUI ("set up ComfyUI first").
  • Only what's missing: a file already in place is only pointed at. A setting that names some other file (klein 9B, say) is the user's choice and is never replaced.
  • Room first: each disk must have room for what's left to download, plus 1 GB to spare, or nothing is downloaded.
  • Resumable: a download goes to <name>.part. The next run reads the .part again (so the sha256 covers the whole file), then asks for the rest with a Range; a server that sends the whole file instead starts it over. A lost connection is retried, up to 5 times in a row while nothing more arrives, waiting 2 s, then twice as long each time. Ctrl+C keeps the .part.
  • Checked, then used: once the size and sha256 match, the .part is renamed into place and the setting points at it: the full path for [text], the file name for [image]. A mismatch deletes the .part. A file that fails doesn't stop the others.

12. GPU memory: the series rule

A GPU that shares memory with the CPU can report far more memory than an 18 GB language model and a 16 GB image model (20 GB for klein 9B) need together. In practice, on Windows with HIP, a large single allocation can fail while the other process holds memory, however much is free overall. So the rule is: one model on the GPU at a time. A night shift writes everything first, gives the GPU back, then renders.

13. Storage

Everything the Angler keeps is in data/ in the home folder (config.DATA, section 14): one SQLite file and one folder of images. db.py opens the database once per process (check_same_thread = False, WAL mode, one RLock around every statement) and runs the schema on every start. Migrations are columns added in place: conn() adds each column in ADDED (devices.role, posts.snagged_at) to a database made before it. First, backup() copies the database as it was to data/backups/baitbook-<date>-<time>.db with SQLite's backup API, since even a source checkout runs on the owner's own data. Only a change makes a copy: a new database is made whole by the schema.

  • A vote is a number on the post. −1, 0 or 1, with when and by whom ("pc" for this machine, or the paired device's name). db.vote only lets a vote through if it was made at or after the stored voted_at, so a phone docking late can't undo a newer vote; a time in the future counts as now. There is no vote history.
  • A snag is a time on the post, not a vote. snagged_at keeps the vote as it was, so undoing a snag restores it. A snagged row stays after purge_snags() has deleted its files and nulled its image (section 8).
  • Seeds are posts. kind = 'seed', shift_id = 0, prompt filled in by the vision read. They are never voted on and are the roots of every edit chain.
  • Deleting a resident (DELETE /api/residents/{id}) deletes their posts and every image file, through db.delete_resident and media.delete.
  • Everything that comes in becomes a PNG. media.save applies the EXIF rotation, writes the PNG master and both JPEG variants, and returns the stem. The apps only ask for the JPEGs, though /media/ would serve a PNG master too; media.path serves any file directly inside data/images/ and refuses every other name.

16. Trust and pairing

There are no accounts, and there are two kinds of caller. The owner is this machine, asked directly, or a PC app on another machine that paired as the owner. A device is a paired phone: it can read, vote and dock, but not steer. client(request) decides who is calling, from where the request came from and the token it carries; owner(request) guards the owner's routes.

What this does and does not protect:

  • The server listens on every interface (host = 0.0.0.0) so phones can reach it. Over plain HTTP, tokens and images cross the Wi-Fi in clear. Behind tailscale serve they travel over HTTPS inside Tailscale's encrypted tunnel, and with host = "127.0.0.1" the plain port is not on the Wi-Fi at all. With ssl_certfile, the Angler encrypts them itself, and its plain-HTTP listener for the PC app (local_port) is bound to 127.0.0.1 only.
  • Wrong codes are limited. After 5 wrong codes in a row, the code changes and pairing pauses for a minute (a 429), with a line in the log and the journal. Since the code changes after every 5 guesses, finding it by guessing would take about 200,000 pauses, over four months, on average. The code is shown only to the owner.
  • Tokens don't expire, but they can be revoked. Settings lists every paired device with a "remove" button (DELETE /api/devices/{id}). The id is made from the device's token (db._public_id), not its database row, so it is never another device's: a "remove" sent again after a new device paired is a 404, not that device's end. "Unpair" on a phone deletes its own token on the Angler (POST /api/unpair) before forgetting it.
  • A phone can read and vote, but not steer. It cannot create residents, change settings or start a shift. A PC app paired as the owner can do everything this machine can, so give the code only to machines you trust.
  • Only this machine can stop the Angler. POST /api/shutdown (baitbook stop) checks is_local() itself, so a phone or a PC app paired as the owner gets a 403.
  • A web page elsewhere is not this machine. Any page open in a browser here, even one served from another port on this machine, can make the browser send the Angler a form or a simple fetch: CORS only stops it reading the answer. So is_local() also asks same_origin(): a request with Sec-Fetch-Site other than same-origin or none, or with an Origin that doesn't name the very Host it was sent to, gets no owner's rights (and, with no token, a 401). The PC app's own page passes; baitbook stop and status send neither header.
  • Bodies have a limit, and the upload is the owner's before it is read. FastAPI reads a request's body, spooling a form's files to disk, before the route runs. The BodyLimit middleware runs first: it turns away a POST /api/residents from anyone but the owner without reading it, and stops any body past MAX_UPLOAD (256 MB, the seed images) or MAX_BODY (8 MB, everything else) with a 413, by its Content-Length or as the bytes come in.
A proxy on this machine is not this machine. A reverse proxy running beside the Angler, such as tailscale serve (the recommended HTTPS setup, which baitbook phone makes: README, "Put it on your phone"), connects from 127.0.0.1 too. is_local() therefore also requires a loopback Host header and no proxy headers, so devices behind the proxy must pair like any other. Serve gives itself away in three ways. It passes on the phone's Host (the PC's ts.net name). It sets X-Forwarded-Host, X-Forwarded-Proto and X-Forwarded-For. And for a person's device (not a tagged one) it adds Tailscale-User-Login, -Name and -Profile-Pic. Uvicorn also replaces the peer address with the one in X-Forwarded-For when the proxy is on 127.0.0.1. One gap is left: a proxy on this machine that sends Host: 127.0.0.1 and adds no forwarding header at all would still look local.

The PC app on this machine skips HTTPS. With [app] angler_url empty, pcapp opens http://127.0.0.1: plus config.local_port(). That is [server] port, or with HTTPS on, the Angler's loopback-only local_port (section 4). No certificate has to name 127.0.0.1: Tailscale's never do, and mkcert's only if asked. Loopback HTTP is already a secure context to the browser, and the Angler sees this machine there, the owner. pywebview's IGNORE_SSL_ERRORS would also open an HTTPS loopback URL, but it accepts every bad certificate the window meets, for any host, so it stays off. reachable() counts a 401 as up (urlopen raises it as an HTTPError). While waiting for the Angler it started, pcapp gives up early if that Angler quits, and shows the log's path; data/angler.log says why, usually that another Angler holds the data folder.

18. The phone app

The phone app in web/device/ is an offline feed. It never asks the Angler for anything while you scroll: everything it shows was brought down at the last dock and lives on the phone. It is a PWA, so it can be added to the home screen: a manifest with an id (/device/), PNG icons (192, 512 and a maskable 512, besides icon.svg), an apple-touch-icon.png for iOS, which ignores SVG, and a service worker. The service worker serves the app's own files from its cache first, so a launch never waits on the network. The Angler serves sw.js with a hash of web/device/ and web/shared/ in it, so a phone picks up a new release the next time it opens the app at home.

  • Images are blobs, not URLs. At the dock the phone downloads both JPEGs of each new post (<stem>.jpg for the feed, <stem>_t.jpg for grids and the reef) and stores them in IndexedDB. At start, warmImages() turns every stored blob into an object URL. Nothing is fetched while scrolling.
  • Votes wait on the phone. S.vote toggles the post's vote, marks it queued (and voteQueued), and records the time. The header pill and the Dock tab badge count what is queued. A double-tap on an image is a bite.
  • So do snags. "✕ snag" (S.snag) marks the post snagged and queued, and every screen reads S.visible(), so it is gone at once. The toast offers undo; the next dock sends the snag home and drops the post. A dock marks every snag it takes out snagSent, so undoing one while that dock is out (or after it failed) keeps the post queued, and the next dock sends unsnag instead. Once a dock has come back the post is gone, and the toast points to the PC app's Ledger.
  • The feed ends. Posts are grouped by night, newest night first, with the seed images last. After that comes an end card: "That's the whole catch." There is no paging and no infinite scroll.
  • On the Angler's own machine there is no pairing. At localhost the page is local (LOCAL in device.js), so it skips the pair screen and docks without a token. That is how it was tested on the PC.
  • Unpairing is real. "unpair" on the Dock screen sends POST /api/unpair, so the token stops working on the Angler, then forgets it. The posts stay on the phone.
  • One browser, one token per Angler. The token lives in localStorage under baitbook.angler, which /app/ and /device/ on the same address share. A browser that paired the PC app as the owner opens the phone app already paired, as the owner.
Offline needs HTTPS. Browsers only run a service worker in a secure context: https://, or localhost. Over plain http://192.168.x.x:8787 the phone still keeps its posts, images and votes in IndexedDB. But the page itself is not cached, so it cannot open with no network. device.js registers sw.js only when window.isSecureContext is true. To get the full offline app on a phone, put the Angler behind tailscale serve (recommended; baitbook phone does it), or set ssl_certfile / ssl_keyfile in [server] (README, "Put it on your phone"). Give the phone an address that won't change, too. The installed app, its cache and its token belong to the origin it was installed from, so a new LAN IP strands it. A MagicDNS name doesn't change.

19. Docking, end to end

A dock is one request. The phone sends the votes it has been holding and the ids of every post it has. The Angler answers with what the phone is missing, what it should let go of, and the current vote on everything it keeps. S.dock in device-store.js on one side and dock() in server.py on the other.

  • A snag leaves the phone at the dock that sends it. The snag goes home first, then the post is no longer in keep, so it comes back in drop. The journal's dock line counts snags apart from votes.
  • A throw-back leaves the phone at the next dock. Its vote goes home first, then it is no longer in keep, so it comes back in drop. The same happens to a post the owner throws back on the PC, and to anything older than keep_nights. Seeds are never dropped.
  • "7 nights" is 7 × 24 hours back from the moment of the dock, by each post's created_at. It is not counted in shifts.
  • Retrying is safe. Votes are values, so if the connection fails after the Angler has stored them, the phone still has them queued and sends them again next time, with the same result.
  • Votes travel both ways. The answer's votes carries the current vote of every kept post the phone has, and the phone takes it. A bite given on the PC shows on the phone after its next dock. A throw-back given on the PC reaches it as a drop.
  • The newer vote wins, not the later request. Each vote carries the time it was made (at, the phone's clock). db.vote skips one older than the vote already stored, so a phone that docks today with a vote from yesterday does not undo what the owner decided this morning. The phone then shows the owner's vote.
  • A missing image is fetched again. If a download fails, the post is stored without it. Every dock looks for kept posts that have no image on the phone and fetches it.

21. The schedule

A night shift can be run by hand from the Night shift tab, or on a schedule. The schedule is a switch, a time and a catch-up window: [shift] schedule_enabled, schedule_time and catch_up_hours, set on the same tab. Engine._scheduler, a daemon thread started with the engine, asks Engine.due() every 20 seconds whether a shift is owed.

  • Catching up. This PC is a laptop. On battery it sleeps after 45 minutes idle, and closing the lid sleeps it at any time; a sleeping machine runs nothing, and nothing here wakes it. When it wakes, or the Angler starts, within catch_up_hours (6 by default) of the scheduled time, the shift runs then, with a journal line saying how late. Past the window, that night is skipped. A shift already run since the scheduled time, scheduled or by hand, counts, so a restart never runs a night twice. Set the window to 0 to only ever run on time.
  • Awake while working. While any job runs, keep_awake() stops the machine idling into sleep halfway through a shift: SetThreadExecutionState on Windows, caffeinate on macOS, and systemd-inhibit on Linux where there is one. It does not stop the lid.
  • Closing the PC app does not stop it. The Angler that pcapp starts runs detached (section 17); baitbook stop ends it. Closing the console of a baitbook angler does stop it.
  • A shift takes minutes. Each post is about 25 s of prompt and caption plus 30 to 100 s of image edit (klein 9B, measured in development). With 3 posts for each of 6 residents, that is roughly 25 to 40 minutes after 03:00.

dockThe phone's one-request sync: queued votes up, new posts down, old ones dropped (POST /api/dock).
keep_nightsHow far back a dock reaches: [device] keep_nights × 24 hours (7 by default).
pairing code, tokenThe 6 digits that let a phone or another PC pair, new at each start and after 5 wrong tries; and the secret it gets in return and sends with every request.
owner, deviceThe two kinds of caller. The owner is this machine, or a PC app paired with role: "owner", and may do everything. A device is a paired phone: it can read, vote and dock.
catch-upRunning a scheduled shift late, when the PC slept through its time or the Angler was off, if it is still within [shift] catch_up_hours.

the ReefA resident's edit graph drawn as coral, seeds on the seabed (web/shared/reef.js).
